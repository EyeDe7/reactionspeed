1. End-to-End 5-Stage Cryptographic Lifecycle Zero-Trust Score Verification

Every score displayed on the leaderboard passes through five cryptographic and biometric verification layers. Neither network packet tampering nor direct SQLite database edits can forge a verified score without detection.

Stage 1 • Local Init
Ed25519 Keypair & Binary Self-Hash
On first launch, the client generates a 256-bit random seed (private_seed_hex), derives its 32-byte Ed25519 public key, and hashes its own executable file on disk via SHA-256.
Stage 2 • Identity
Public-Key Binding (/auth/register)
The client registers its nickname, public_key, and binary_sha256. The server binds the nickname to that Ed25519 public key and stores only SHA-256(api_token).
Stage 3 • Pre-Round
Signed Challenge Ticket (/challenge)
Before Round 1, the client Ed25519-signs CHALLENGE|id|ts|sha. The server verifies the signature & clock skew and issues a single-use challenge_nonce + 5 random wait delays.
Stage 4 • Submission
Dual Signing (/submit)
After 5 rounds, the client builds the 10-field canonical_payload and signs it twice: an asymmetric Ed25519 player signature and a 2-stage HMAC-SHA256 binary attestation.
Stage 5 • Ledger
SHA-256 Hash-Chain Block
The server verifies wall-clock timing, biometric bounds, HMAC, and Ed25519 signature, then commits the score into an append-only SHA-256 hash chain linked to prev_hash.

3. Ed25519 Asymmetric Signatures (RFC 8032) 128-bit Security

Each player's identity is anchored by an Ed25519 keypair operating over the Twisted Edwards curve birationally equivalent to Curve25519 over the prime field 𝔽p where p = 2255 - 19:

-x² + y² ≡ 1 - (121665 / 121666) · x² · y² (mod 2²⁵⁵ - 19)
Base Point Order L = 2²⁵² + 27742317777372353535851937790883648493

Step A: Key Derivation & Bit Clamping

From the player's 32-byte random seed k (private_seed_hex), the client computes a 64-byte digest h = SHA-512(k). The lower 32 bytes h[0..31] are clamped to form the secret scalar s, clearing the curve cofactor (8) and fixing the top bit:

SHA512(seed[0..31]) -> d[0..63] d[0] &= 248; // Clear lowest 3 bits (cofactor = 8) d[31] &= 127; // Clear bit 255 d[31] |= 64; // Set bit 254 (fixed scalar length) PublicKey A = PackPoint( ScalarBaseMult(B, d[0..31]) );

Step B: Deterministic Signing (Why Re-Signing Matches Byte-for-Byte)

Unlike ECDSA (which requires a random per-signature nonce k that can leak the private key if reused), Ed25519 derives its ephemeral nonce r deterministically using the upper 32 bytes d[32..63] and the message M (canonical_payload):

r = SHA512(d[32..63] || M) mod L R = PackPoint( [r]B ) // 32-byte point commitment k = SHA512(R || PublicKey_A || M) mod L // Fiat-Shamir challenge scalar S = (r + k * s) mod L // 32-byte response scalar Signature = Hex( R[0..31] || S[0..31] ) // 64 bytes (128 hex chars)

Why this matters for the Website Auditor: Because r and S are 100% deterministic functions of private_seed_hex and canonical_payload, pasting your private seed into the homepage auditor re-runs the signing equation and proves that the freshly generated 128-character signature matches the database signature byte-for-byte.

4. Binary Self-Attestation & Two-Stage HMAC Client Integrity

A valid player key alone is not enough—the server also verifies that the score was produced by an unmodified, official client executable.

Step A: Runtime Executable Self-Hashing

Immediately upon launch (main()), the binary resolves its own kernel executable path and streams its binary image through SHA-256 in 8,192-byte chunks:

// Linux: resolves kernel symlink readlink("/proc/self/exe", buf, PATH_MAX); // Windows: resolves loaded PE module path GetModuleFileNameA(nullptr, buf, MAX_PATH);

Step B: Two-Stage Key-Derived HMAC-SHA256

When submitting a 5-round set, the client reconstructs its obfuscated 256-bit protocol secret (Kproto) in memory (enc[i] ^ (0x5A + i * 7)) and performs a two-stage HMAC-SHA256 derivation bound to the single-use challenge_nonce:

// Stage 1: Derive per-challenge ephemeral attestation key attest_key = HMAC_SHA256( K_proto, binary_sha256 + ":" + challenge_nonce + ":" + api_token ); // Stage 2: Authenticate the canonical score payload attestation_hmac = HMAC_SHA256(attest_key, canonical_payload);

The server independently recomputes expected_attest and compares it in constant time via hmac.compare_digest() to prevent timing side-channel attacks.

5. Challenge-Response Protocol & Wall-Clock / Biometric Anti-Cheat Replay & Bot Protection

To prevent pre-computed payloads, packet replays, pixel-trigger bots, and fixed-interval macros, the server controls the random wait delays for every round and validates real-time elapsed wall-clock duration.

6. Cross-Platform Native Crypto Engine Linux & Windows Parity

Both desktop binaries produce identical SHA-256 digests, HMAC-SHA256 tags, and RFC 8032 Ed25519 signatures:

  • Linux (reaction_benchmark_linux_x86_64): Uses hardware-accelerated OpenSSL libcrypto (EVP_DigestInit_ex with EVP_sha256(), HMAC(), and EVP_PKEY_ED25519 raw key derivation & signing).
  • Windows (reaction_benchmark.exe): To run as a zero-dependency standalone .exe with no external DLLs, crypto.hpp embeds a self-contained C++20 implementation of SHA-256, SHA-512, HMAC-SHA256, and radix-216 Ed25519 group arithmetic (gf = int64_t[16]) with branchless constant-time conditional point swaps (cswapPoint / sel25519).
  • Server Verifier (server.py): Verifies all signatures using Python's OpenSSL-backed cryptography.hazmat.primitives.asymmetric.ed25519.Ed25519PublicKey.
